# Авторусь Сигнал на Laravel Octane

PHP-сервис управления уведомлениями. Требуется PHP 8.4 с расширениями `pdo_pgsql`, `sockets`, `pcntl`, `dom`, `xmlreader` и `zip`, Composer, PostgreSQL и FrankenPHP для запуска Octane. Для запуска в Windows достаточно `php artisan serve` без Octane, которому нужен `pcntl`. Используйте отдельную базу для разработки.

```bash
cd laravel
cp .env.example .env
composer install
php artisan key:generate
php artisan migrate
php artisan octane:start --server=frankenphp --host=127.0.0.1 --port=8000
```

Перед миграцией задайте параметры PostgreSQL в локальном `.env`. Для API задайте случайный токен в `HOMER_API_TOKEN`. Например, его можно сгенерировать командой `php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'`.

Для входа в `/admin` задайте хеш пароля в `HOMER_ADMIN_PASSWORD_HASH`. Блок ниже читает пароль из терминала и выводит хеш. Хеш в `.env` заключите в одинарные кавычки.

```bash
read -rsp 'Пароль админки: ' admin_password
printf '%s' "$admin_password" | php -r 'echo password_hash(stream_get_contents(STDIN), PASSWORD_DEFAULT), PHP_EOL;'
unset admin_password
```

Docker-образ собирается командой `docker build -t homer-octane .` из этого каталога. Для корпоративного прокси можно передать доверенный CA bundle через `docker build --secret id=composer_ca,src=/path/to/ca-bundle.pem -t homer-octane .`.

```bash
curl -fsS http://127.0.0.1:8000/ping
curl -fsS -X POST http://127.0.0.1:8000/api/v1/message \
  -H "Authorization: Bearer ${HOMER_API_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"eventId":"local-smoke","recipientId":"0000","content":"Test"}'
curl -fsS -H "Authorization: Bearer ${HOMER_API_TOKEN}" \
  'http://127.0.0.1:8000/api/v1/message?eventId=local-smoke'
```

Для запросов из терминала предварительно экспортируйте тот же токен. В управлении каналами поле `config` можно передать при создании или обновлении. Оно хранится зашифрованным. API и админка возвращают пустой объект для `config` и пустую строку для `applicationFirebaseToken`. При обновлении пропуск поля или передача такого пустого значения сохраняет исходные данные. Чтобы очистить поле явно, передайте `null`.

В `/admin` можно искать и редактировать каналы, сценарии, получателей, уведомления и отправки. Для уведомлений и отправок доступен фильтр по статусу, а журнал доставки доступен для чтения. В формах есть отдельные поля для основных параметров. JSON используется для вложенных настроек, правил и метаданных. Вход использует общий пароль админки. Смена его хеша завершает действующие сеансы при следующем обращении.

Поиск по части строки в уведомлениях и отправках использует индексы PostgreSQL `pg_trgm`. Для первой установки расширения роль миграций должна иметь право `CREATE` на базе. Если роль ограничена, администратор PostgreSQL может заранее выполнить `CREATE EXTENSION IF NOT EXISTS pg_trgm WITH SCHEMA public` в базе приложения. Для установки расширения нужен пакет PostgreSQL с дополнительными расширениями. Индексы строятся параллельно с обычными чтениями и записями. На большой истории миграции потребуется больше времени и дискового пространства.

В каждом разделе с редактированием доступны импорт и экспорт XLSX, CSV и JSON. Файл импорта может содержать до 1000 записей и занимать до 2 МБ. Если одна строка не проходит проверку, весь импорт откатывается. Экспорт скрывает настройки каналов и токены Firebase.

Для импорта таблиц начните с файла, выгруженного из нужного раздела. В CSV используйте UTF-8, запятую или точку с запятой. В XLSX данные читаются с первого листа. Телефоны и идентификаторы храните в текстовых ячейках, вложенные поля записывайте как JSON. Формулы читаются как текст. Если нужен результат формулы, замените её значением в Excel. Пустые ячейки оставляют действующие значения без изменений. Поле `scenario` из старых таблиц уведомлений принимается как `scenario_id` с UUID сценария. Поле `message` при переносе отправок должно ссылаться на ID уведомления в целевой базе.

Если текст превышает ограничение Excel в 32 767 символов на ячейку, админка предлагает выгрузить CSV или JSON. Эти форматы сохраняют текст целиком.

## Запуск через Docker Compose

`compose.yaml` поднимает PostgreSQL, RabbitMQ, Octane, потребитель и планировщик. Миграции выполняются отдельным процессом до старта приложения. HTTP доступен на `127.0.0.1`. PostgreSQL и RabbitMQ доступны по внутренней сети Compose.

```bash
cd laravel
cp .env.compose.example .env.compose
chmod 600 .env.compose
docker build -t homer-octane:local .
docker compose --env-file .env.compose up -d --wait
```

Перед `up` заполните `.env.compose`:

- `APP_KEY` состоит из префикса `base64:` и результата `openssl rand -base64 32`. Храните этот ключ вместе с резервными копиями базы. Он нужен для чтения зашифрованных настроек каналов.
- `POSTGRES_PASSWORD` и `RABBITMQ_PASSWORD` заполните разными результатами `openssl rand -hex 24`. Для пароля RabbitMQ используется шестнадцатеричный формат, чтобы он корректно входил в AMQP URL.
- Для `HOMER_API_TOKEN` используйте результат `openssl rand -hex 32`. Для веб-админки дополнительно задайте `HOMER_ADMIN_PASSWORD_HASH` в одинарных кавычках по инструкции выше.

Чтобы использовать готовый образ, укажите его в `HOMER_IMAGE` и пропустите сборку. Команды `docker compose --env-file .env.compose ps -a` и `docker compose --env-file .env.compose logs migrate web consumer scheduler` показывают состояние процессов. Остановка через `docker compose --env-file .env.compose down` сохраняет именованные тома. При обновлении старой установки, где RabbitMQ запускался без фиксированного имени узла, перенесите данные брокера на узел `rabbit@rabbitmq` перед пересозданием контейнера.

## Приёмка в тестовой среде

1. Соберите образ из зафиксированного коммита и используйте выделенные тестовые PostgreSQL и RabbitMQ. Для Compose подготовьте отдельный `.env.compose`. Используйте тестовые секреты и отдельный ключ приложения. Внешний HTTPS-прокси может направлять запросы на локальный порт Compose.
2. После запуска проверьте, что миграции завершились с кодом 0, а `web`, `consumer` и `scheduler` работают. `GET /ping` проверяет веб-процесс. `GET /ready` проверяет соединение с PostgreSQL и возвращает HTTP 503 при сбое. Готовность RabbitMQ и планировщика проверяется отдельно сквозной отправкой.
3. Настройте один тестовый канал и согласованный тестовый адрес получателя. Отправьте синтетическое уведомление через API или RabbitMQ со стабильным `eventId`. Повторите запрос с тем же ID и проверьте, что в базе одна запись уведомления и одна отправка для выбранного канала. Сверьте полученный идентификатор и итоговый статус у провайдера, если канал их поддерживает.
4. Повторите проверку для каждого провайдера первого релиза. Зафиксируйте час запуска, ID уведомления и результат. Проверяйте в журнале код сбоя, не включая в отчёт секреты, тело сообщения и адрес получателя.

## Фоновая обработка и доставка

Запускайте веб-процесс Octane, потребитель RabbitMQ и планировщик отдельными процессами. Для штатной работы потребителя настройте перезапуск после завершения процесса. Для RabbitMQ задайте `RMQ_BROKER_URL` и `RMQ_CREATE_MESSAGE_EXCHANGE`. Потребитель объявляет долговечные direct exchange и очередь с одним именем и пустым routing key. Поддерживаются `amqp` и `amqps`. Для защищённого соединения сертификат брокера должен быть доверен средой PHP.

```bash
php artisan homer:consume
php artisan schedule:work
```

Сообщение подтверждается в RabbitMQ после транзакции PostgreSQL. Повтор с тем же непустым `eventId` не создаёт дубликат. Отправитель должен задавать стабильный `eventId` для каждого уведомления, которому требуется дедупликация. Некорректный JSON или данные отклоняются без возврата в очередь. Для их хранения настройте политику dead letter на RabbitMQ. При сбое базы необработанное сообщение остаётся без подтверждения, а потребитель завершается.

Планировщик подготавливает записи отправки и обрабатывает отправки, для которых наступил срок. Команды также доступны для разового запуска.

```bash
php artisan homer:prepare --limit=100
php artisan homer:deliver --limit=10
```

Для автоматической очистки задайте `HOMER_PURGE_EXPIRED=true` и запустите планировщик. Он проверяет срок хранения раз в минуту и удаляет просроченные уведомления вместе со связанными отправками. Уведомления с отправками, которые сейчас обрабатывает воркер, пропускаются. По умолчанию автоматическая очистка выключена. Для разового запуска используйте `php artisan homer:purge-expired --limit=1000`.

Попытки доставки координируются через PostgreSQL. При подтверждённом временном отказе, например HTTP 429, используется отложенный повтор с ограниченным числом попыток. При неопределённом результате, таком как тайм-аут вызова провайдера, запись отмечается для разбора без автоматической повторной отправки. Админка показывает число попыток и код последнего сбоя.

| Канал | Параметры `config` |
| --- | --- |
| SMTP | `server`, `port`, `ssl`, `email` и при необходимости `user`, `password`. Требуется TLS. |
| Telegram | `token`. Для тестового сервера можно задать `apiBaseUrl`. |
| IDGTL | `url`, при необходимости `method`, `headers`, `senderName`. По умолчанию `POST`. |
| Retail Rocket | `url`, `method`, `apikey` или `apiKeyValue`. `campaignId` берётся из метаданных уведомления. |
| Firebase | Объект `serviceAccount` с `project_id`, `client_email` и `private_key` для HTTP v1. Для отдельного шлюза, принимающего старый формат, укажите `url` и при необходимости `method` и `headers`. По умолчанию `POST`. |
| Notices | `url`, при необходимости `method` и `headers` для HTTP. Для AMQP дополнительно нужен `exchange` и при необходимости `routingKey`. Получатель должен сам объявить и привязать очередь к exchange. |

Проверка с реальными провайдерами и полная сверка API с работающим Django остаются в работе.

## Управление уведомлениями и отправками

API поддерживает создание и чтение `/api/v1/message` и `/api/v1/sending`, а также `PUT`, `PATCH` и `DELETE` по числовому ID. `PUT` отправки требует `channel` и `content`. Уведомление можно создать без `recipientId`, если сценарий получает адрес назначения из `metadata`. Прямой `DELETE` уведомления сохраняет связанные отправки, отсоединяя их от уведомления. Для удаления вместе с отправками существует `PATCH /api/v1/message/bulk/remove`.

Изменение занятой воркером отправки и удаление такой отправки напрямую или в составе пачки возвращают HTTP 409. Пометка уведомления на удаление приостанавливает его ожидающие отправки. Запрос пометки возвращает HTTP 409, если хотя бы одну из них уже обрабатывает воркер. Отправка без адреса назначения ждёт заполнения адреса до истечения срока.

`GET /api/v1/eventlog` и `GET /api/v1/eventlog/{id}` доступны для чтения журнала доставки. Запись о сбое содержит код причины и идентификатор отправки.

Если выбран сценарий, используются только его правила. Когда ни одно правило не подходит или указанный сценарий отключён, уведомление получает статус «Не отправлено». Прямой список `channels` применяется, когда сценарий не указан и для типа уведомления нет активного сценария по умолчанию. После завершения всех отправок общий статус уведомления показывает сбой, если хотя бы один канал завершился ошибкой или просрочен.

Колбэк `PATCH /api/v1/sending/status` принимает числовые статусы от 3 до 8 и поддерживаемые текстовые статусы провайдеров. Коды очереди от 0 до 2 возвращают HTTP 400. Для занятой воркером отправки колбэк возвращает HTTP 409. Если идентификатор провайдера совпал у нескольких отправок, укажите код канала в поле `channel`. Если запись по-прежнему неоднозначна, API возвращает HTTP 409. Повторите запрос после завершения попытки. Ошибка в пакетном колбэке оставляет всю пачку без изменений.

Для регрессионной проверки колбэков и удаления используйте отдельную PostgreSQL с применёнными миграциями.

```bash
APP_ENV=testing php tests/delivery-regression.php
```

Проверка вызывает HTTP-обработчики Laravel и откатывает синтетические записи в конце.

## Сверка с Django

Запустите обе версии на отдельных тестовых базах с применёнными миграциями. Установите `HOMER_API_TOKEN` для тестового Laravel, затем передайте скрипту базовые URL обеих версий.

```bash
python3 tests/compare-api.py http://localhost:8001 http://localhost:8000
```

Скрипт выполняет HTTP-запросы с синтетическими данными и выводит различия в статусах и JSON. Код возврата 1 означает расхождения, 2 означает, что проверку не удалось полностью выполнить из-за отсутствия записи для следующих запросов. При сравнении игнорируются сгенерированные ID и служебные даты верхнего уровня. Размер страницы, даты доставки и вложенные поля JSON сравниваются.

Правила совместимости с Django

- Формат полей `config` и `applicationFirebaseToken` совпадает с Django, а сохранённые значения скрыты. API требует Bearer-токен.
- Обязательные поля возвращают код `required` и сообщение «Обязательное поле.». Формулировки других ошибок валидации могут отличаться.

Как и в Django, параметр `limit` ограничивает число записей в ответе, а `meta.limit` содержит размер страницы по умолчанию (100).

Маршрут `GET /openapi/` публикует JSON-описание Laravel API в формате OpenAPI 3.0.3.

Маршрут `GET /metrics` публикует метрики Prometheus `homer_messages_statistics`, `homer_sendings_statistics_status` и `homer_sendings_statistics_channel`. Счётчики включают известные статусы и каналы с нулём записей. Маршрут доступен без API-токена.

## Автоматическая проверка

GitHub Actions собирает Docker-образ, проверяет зафиксированные зависимости Composer на известные уязвимости и запускает проверку на отдельном стеке Compose. Она проверяет миграции, регрессии API, приём уведомления из RabbitMQ, дедупликацию и публикацию результата планировщиком, а также отказ и восстановление PostgreSQL. Тестовые тома удаляются по завершении.

Для локального запуска передайте имя уже собранного образа.

```bash
bash tests/smoke-compose.sh homer-octane:local
```
